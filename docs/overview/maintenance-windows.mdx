Keep's Maintenance Windows suppress expected alerts during planned work so operators are not paged for noise. New rules **keep matching alerts in the feed as `suppressed`**. Hiding alerts from the feed (not persisting them) is an explicit choice.

</Frame>

## How it works

1. Create a rule with a CEL filter, start time, and duration.
2. While the rule is **enabled** and **now** is between start and end, incoming alerts are evaluated against the CEL query.
3. Matching alerts are either:
   - **Show in feed as suppressed** (default): saved with status `suppressed` (or `maintenance` when recover strategy is on). Workflows and incident correlation are skipped.
   - **Hide from feed**: dropped before save. No alert row, no workflow, no incident.
4. Alerts whose status is in **Do not suppress these statuses** (default: `resolved`, `acknowledged`) always continue so incidents can close.
5. When several rules match, the highest **priority** wins (then lowest id).

Resolved and acknowledged alerts bypass the window on purpose. A resolve event during maintenance still closes the related incident.

## Create a rule

  <img height="10" src="/images/maintenance-window-creation.png" />
</Frame>

1. **Name / description** — shown in audit logs.
2. **CEL filter** (required) — which alerts match. Use `true` to match all. Shortcuts in the form insert common queries (`source`, `service`, `code`).
3. **Do not suppress these statuses** — exclusions. Leave Resolved and Acknowledged selected unless you intentionally want those silenced too.
4. **Start at / End after** — the form shows the computed end time in your browser timezone. Duration is stored in seconds; editing infers minutes, hours, or days.
5. **Priority** — higher number wins when rules overlap.
6. **Alert handling**
   - **Show in feed as suppressed** (default, recommended)
   - **Hide from feed (do not persist)** — matching alerts are not saved
7. **Enabled** — disabled rules never match, even inside the time range.

The form previews how many alerts from the last 24 hours would match the CEL query.

You can also create a window from **Noise Reduction → Service Topology**: click a node, choose a reason (node down, RMA, firmware/driver upgrade, thermal/cooling, planned capacity work, or Other) and duration, then **Put node in maintenance**. Keep writes the same Maintenance Windows rule with a CEL filter scoped to that node (`labels.host`, `labels.rack`, `labels.gpu_id`, and so on). The node is color-coded on the map while the window is active.

If an [approval policy](/overview/approvals) matches `create_maintenance` or `node_maintenance`, Keep returns **202** and the window is not active until an approver accepts it in **Approvals**.

## Lifecycle

Each rule has a status:

| Status | Meaning |
|---|---|
| **Upcoming** | Enabled, start time is in the future |
| **Active** | Enabled and now is inside the window |
| **Expired** | End time has passed |
| **Disabled** | Enabled is off (including after **End now**) |

On an active rule you can:

- **End now** — disable the rule and set end time to now
- **Extend +30m** — push the end time forward 30 minutes (and re-enable if it had expired)

A window is expired when **end time has passed OR the rule is disabled**. Either condition is enough.

## CEL examples

```cel
source == "prometheus"
service == "gpu-node-03"
code == "GPU_XID_79"
source.contains("kibana")
true
labels.host == "gpu-node-a03" || service == "gpu-node-a03"
labels.gpu_id == "gpu-node-a03-gpu0"
labels.rack == "rack-12"
```

If an alert has a single source, Keep treats `source` as a string (`source == "prometheus"`). Multiple sources stay a list; use `source.exists(s, s == "prometheus")`.

## Strategies

### Default (`MAINTENANCE_WINDOW_STRATEGY=default`)

Matching alerts that use **Show in feed as suppressed** are stored as `suppressed`. They stay that way when the window ends.

### Recover previous status (`MAINTENANCE_WINDOW_STRATEGY=recover_previous_status`)

Requires **Show in feed as suppressed**. Matching alerts are stored as `maintenance` and workflows/incidents are skipped. A watcher (every `KEEP_WATCHER_LAPSED_TIME` seconds, default 60) restores the previous status when the window expires or is disabled, then runs workflows and correlation as if the alert just arrived.

Setting `MAINTENANCE_WINDOW_STRATEGY=recover_previous_status` starts the watcher automatically. You do not need a separate `MAINTENANCE_WINDOWS=true` flag for recover to run.

## Environment variables

| Env var | Purpose | Default |
|---|---|---|
| `KEEP_MAINTENANCE_WINDOWS_ENABLED` | Apply rules on ingest | `true` |
| `MAINTENANCE_WINDOW_STRATEGY` | `default` or `recover_previous_status` | `default` |
| `KEEP_WATCHER_LAPSED_TIME` | Recover poll interval (seconds) | `60` |
| `WATCHER` | Start the watcher for other jobs | `false` |
| `MAINTENANCE_WINDOWS` | Also start the watcher (legacy) | `false` |

## Best practices

- Prefer **Show in feed as suppressed** so you keep a record of what fired during the window.
- Keep CEL specific (`service == "gpu-node-03"` rather than `true`).
- Do not clear Resolved/Acknowledged exclusions unless you intend to block incident close.
- Use **End now** when work finishes early instead of deleting the rule if you still want the audit trail.

## Troubleshooting

- **Incidents never close during a window** — restore Resolved (and usually Acknowledged) in **Do not suppress these statuses**.
- **Alerts stuck in `maintenance`** — recover strategy is on but the watcher is not running. Set `MAINTENANCE_WINDOW_STRATEGY=recover_previous_status` (the API starts the watcher) or set `WATCHER=true`.
- **Nothing was silenced** — check lifecycle is **Active**, the rule is enabled, and CEL matches (use the preview count).
