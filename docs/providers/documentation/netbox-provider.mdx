## Overview

NetBox is the leading solution for modeling and documenting modern networks. By combining the traditional disciplines of IP address management (IPAM) and datacenter infrastructure management (DCIM) with powerful APIs and extensions, NetBox provides the ideal "source of truth" to power network automation.

Keep uses NetBox in two ways:

1. **Webhook events** — NetBox Event Rules POST change events into Keep as alerts (no API token required).
2. **DCIM topology sync** — when the provider is configured with a NetBox URL and API token, Keep pulls region / site / location / rack / device / GPU / network objects into [Service Topology](/overview/servicetopology).

## Connecting NetBox to Keep

To connect NetBox to Keep, you need to create a webhook in NetBox.

1. Go to NetBox dashboard, click on `Webhooks` under `Operations` section in the sidebar.

2. Add a new webhook by clicking on `Add` button.

3. Enter [https://api.keephq.dev/alerts/event/netbox](https://api.keephq.dev/alerts/event/netbox) as the URL and select the request method as `POST`.

4. Follow the below steps to create a new API key in Keep.

5. Go to Keep dashboard and click on the profile icon in the botton left corner and click `Settings`.

  <img height="10" src="/images/netbox-provider_4.png" />
</Frame>

6. Select `Users and Access` tab and then select `API Keys` tab and create a new API key.

<Frame width="100" height="200">
  <img height="10" src="/images/netbox-provider_5.png" />
</Frame>

7. Give name and select the role as `webhook` and click on `Create API Key`.

<Frame width="100" height="200">
  <img height="10" src="/images/netbox-provider_6.png" />
</Frame>

8. In the `Additional headers` field enter `X-API-KEY` as the key and the API key generated in step 7 as the value. It should look like below. Refer the screenshot from step 3.

```
X-API-KEY: your-api-key
```

9. Disable the `SSL verification` (Optional) or enable it based on your requirement.

10. Click on `Save` to save the webhook.

11. Go to `Event Rules` under `Operations` section in the sidebar and click on `Add` button to create a new event rule.

<Frame width="100" height="200">
  <img height="10" src="/images/netbox-provider_8.png" />

<Frame width="100" height="200">
  <img height="10" src="/images/netbox-provider_9.png" />

13. In the `Action type` select `Webhook` and select the webhook created in step 3 and click on `Save`.

Now, you have successfully connected NetBox to Keep. You will start receiving the events in Keep based on the event rules you have created.

## Syncing DCIM topology

Webhook ingest does not update the topology map. To pull the datacenter graph, install (or update) the NetBox provider with:

| Field | Required for topology | Description |
| --- | --- | --- |
| `netbox_url` | yes | Base URL, for example `https://netbox.example.com` |
| `api_token` | yes | Token with DCIM and IPAM read permissions |
| `verify_ssl` | no | TLS verification (default on) |
| `gpu_name_pattern` | no | Regex used to detect GPU inventory items and modules |

Then open **Noise Reduction → Service Topology → Pull**, or wait for the provider pull loop when pulling is enabled. Each pull **replaces** nodes previously owned by this NetBox provider (manual nodes are left alone).

### Local Docker Compose (NVIDIA GPU demo)

`make start` starts NetBox at [http://localhost:8000](http://localhost:8000) (`admin` / `admin`) next to the provider mock. First boot takes 1–2 minutes.

1. Open [http://localhost:8099](http://localhost:8099) → **Service Topology**.
2. Wait until **Refresh NetBox status** succeeds.
3. Click **Configure Keep with NetBox** (seeds DCIM, installs this provider with `netbox_url=http://localhost:8000` and the compose API token, then pulls).

The seeded inventory matches the mock Grafana labels: `us-west-2` / `ai-dc-1` / `row-a` / `rack-12` / `gpu-node-a03` / `gpu-node-a03-gpu0`. See [Provider mock](/development/provider-mock) and [NVIDIA GPU Service Topology](/overview/nvidia-gpu-topology).

Production Keep should point at your existing NetBox; do not run this demo compose file as a production DCIM.

### Object mapping

Keep topology is a named-node graph. NetBox objects become nodes whose `service` id should match Grafana alert labels (`host`, `rack`, `row`, `datacenter`, `region`, `gpu_id`).

| NetBox | Keep `category` | `service` id | Depends on |
| --- | --- | --- | --- |
| Region | `region` | slug | parent region (`located-in`) |
| Site | `datacenter` | slug | region (`located-in`) |
| Location | `row` | slug | parent location or site (`located-in`) |
| Rack | `rack` | slug or name | location or site (`located-in`) |
| Device | `host` | hostname | rack (`power`) or location/site |
| GPU inventory item / module | `gpu` | `{host}-gpu{index}` | host (`PCIe`) |
| Prefix | `network` | CIDR | site (`located-in`), VLAN (`L2`) |
| VLAN | `network` | `vlan-{vid}` | site (`located-in`) |
| Device primary IPv4 in a prefix | — | — | host → prefix (`L3`) |

Sites are grouped into a topology application named `NetBox {site}`.

### GPU detection

NetBox has no first-class GPU type. Keep treats an inventory item or module as a GPU when its name, role, part ID, or manufacturer matches `gpu_name_pattern` (H100, A100, L40, NVIDIA, …). If a device has no GPU components, a numeric `gpu_count` custom field synthesizes `{host}-gpu0` … `{host}-gpuN-1`.

Name racks, locations, and hosts so they match the labels your alerts already send. The NVIDIA GPU demo uses `ai-dc-1`, `row-a`, `rack-12`, `gpu-node-a03`, `gpu-node-a03-gpu0`. See [NVIDIA GPU Service Topology](/overview/nvidia-gpu-topology).

<Tip>
  Webhook events such as "rack created" still show up as alerts. They do not patch the map; pull topology again after DCIM changes.
</Tip>
